# Skills release and installation

This operational projection covers independently released Skill files and their local ownership. Source configuration and release workflow remain authoritative: the root `[tool.svc.corpus].version`, per-Skill release metadata, `tools/build_corpus_archive.py`, and `.github/workflows/publish-corpus.yml`. CLI packaging uses only the `cli/` member and never reads or bundles Corpus guidance.

From v16, each `corpus-v<version>` Release publishes six `<skill-name>-<version>.zip` archives, their adjacent `.sha256` files, and `svc-skills-<version>.json` with its own `.sha256`. Each ZIP contains only the complete `<skill-name>/` source directory, including `SKILL.md`, LICENSE, and local resources; it has no `corpus/` wrapper or injected manifest. Third-party archive consumers can install a ZIP without interpreting the catalog. The schema-2 catalog binds the common version, repository, and revision to each Skill’s path, file hashes, archive name, and archive SHA-256. All assets, the tag, and release notes bind to the same committed source. The builder checks source closure and byte equality; published assets are not overwritten with different content. Publication starts as a draft, verifies existing or uploaded assets, then makes the Release public. A rerun resumes the same release identity. CLI `check` queries the Corpus release stream rather than GitHub's repository-wide latest release, which may be a CLI release.

Codex project and user roots are `.agents/skills` and `~/.agents/skills`; Claude Code roots are `.claude/skills` and `~/.claude/skills`. These follow the respective [Codex discovery contract](https://learn.chatgpt.com/docs/build-skills) and [Claude Skill locations](https://code.claude.com/docs/en/skills). Project installation is the default and host selection is explicit for mutations. Skill content is copied unchanged from the release, including its MIT notice. Each Skill's independent record lives at `<skills-root>/.svc/<name>.json`; foreign managers' files and locks are never adopted as CLI-owned installation state.

A complete tree matching its recorded baseline is clean; an absent record, unexpected file, modified bytes, missing content, invalid record, or symlink produces a qualified observation rather than a completed upgrade. `actual_version` is confirmed against a target release, while `recorded_version` only identifies recorded installation intent. Online installation and updates validate the catalog and download only the selected Skill ZIPs; checking can compare the catalog’s file hashes without downloading Skill bodies. Offline standalone ZIPs require the matching release catalog, found beside a canonically named ZIP or supplied with `--catalog`, and the catalog’s adjacent `.json.sha256`. The catalog’s archive digest validates the ZIP; `--checksum` can additionally validate a separate ZIP checksum file. Legacy aggregate ZIPs still require their adjacent or explicitly supplied ZIP checksum. A single offline ZIP selects its own Skill by default. Checksums detect integrity errors; they do not authenticate an arbitrary user's supplied archive as an official publication. Online resolution uses the official repository's release endpoints.

A mutation applies one Skill and its record as a local file transaction. All selected targets undergo conflict preflight before writing. A runtime failure stops later work, rolls back the current unit conditionally, and preserves completed units. A concurrent external change is preserved during rollback. Process-controlled errors and interrupts have rollback support; SIGKILL and power loss have no durable transaction journal. Inspect after such interruption, preserve conflicting or unrecorded remnants, and resolve their ownership before retrying. Do not delete them merely to make an installation appear clean.

The release catalog validates the complete six-name release set, including `svc-workflow`, independent `svc-verification`, and `svc-agent-collaboration`. The earlier `svc-methods` and `svc-sub-agents` entries were development drafts before v15 publication, not separate releases; archives using those draft layouts are rejected. Explicit status and removal still use the original installed name and its file record, so retired installations can be inspected and removed without a runtime alias. Replacing a Skill name requires separate removal and installation plans, then a project adoption refresh; update does not rename directories or silently migrate Consumer instructions. Use the [Skills adoption guide](../../corpus/migrations/agent-skills.md) for the Workflow transition and the [Agent collaboration guide](../../corpus/migrations/agent-collaboration.md) for the collaboration transition.

Project adoption is a separate exact plan on `AGENTS.md` for Codex or `CLAUDE.md` for Claude. It creates the standing non-trivial Task Packet rule and actual entry pointers, protects modified blocks and unmarked Consumer content, and does not transfer ownership of installed files. Unadopting a project never removes a global installation; removing files never silently removes the project's standing rules. A file upgrade directs the operator to release notes and applicable migration guidance rather than applying arbitrary Consumer semantic changes.

The v16 CLI can still read the published v15 aggregate ZIP and its installation records. Online legacy resolution is limited to that known release, rather than falling back after an arbitrary download or validation failure. Future Releases do not publish aggregate ZIPs; CLI 15 must be upgraded before consuming them. This is a release-format boundary, not a Skill rename or an automatic Consumer migration. Installation content identity depends on repository, version, revision, and file hashes; the original archive digest remains provenance and an exact-plan input, so equivalent packaging does not by itself make installed content outdated.
