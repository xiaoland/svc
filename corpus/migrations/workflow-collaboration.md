# Adopt Explicit Staged Collaboration

Target Corpus release: 17.0.0.

Use this guide when adopting the default collaboration workflow from Corpus 16.0.1 or earlier. The former summary combined requirements, solution choices, judgment basis, and authorization in one Clarify and confirm stage. The default now separates Product requirements design, Technical solution design, Acceptance design, Implementation preparation, Realize with feedback, and Verify and deliver. An established project or Task agreement or direct Human instruction still takes precedence, including an agreement to use iterative collaboration.

Keep the rule to read and use [svc-workflow](../svc-workflow/SKILL.md), [svc-task-packet](../svc-task-packet/SKILL.md), and [svc-specs](../svc-specs/SKILL.md) for every non-trivial Task in the Consumer's persistent instructions. Point to the actual adopted entries. The description summarizes collaboration workflows and working methods with this task-level use condition; questions about workflow are not a separate trigger. The [root instruction asset](../svc-specs/assets/AGENTS.root.template.md) supplies the starting shape. Workflow itself owns the protocol; adopting the revision does not require copying its stage rules into Consumer instructions. Catalog wording alone cannot guarantee host selection.

The entry determines the result currently due before methods, tools, or Agent assignments are chosen. A new capability request describes the overall goal; with no applicable stage decisions, current work is Product requirements design. Complete its reviewable result and return it when progression awaits Human authorization, keeping the overall Task's remaining work pending. This is normal fulfillment of the current work, not abandonment of a feature Task. Effect authority for source changes does not by itself cancel stage reviews.

Read the entry's stage-interaction reference for help developing a proposal with the Human or interpreting feedback and stage authorization. Starting or resuming the default workflow does not require loading every reference. Reuse guidance already read and still applicable. Collaboration governs the current result and its return conditions, while Explore, Design, Planning, and Implementation serve that result recursively. Candidate sketches and investigations can develop a proposal before it is ready for stage review; they do not authorize another stage's delivery or effects.

Verification design methods belong to `svc-verification`: designing criteria, conditions, observations, and any facilities needed to judge the result. Workflow retains the Acceptance design stage and its review result, and discovers Verification by name when guidance is needed. Existing evidence can still satisfy the current decision; designing an observation does not establish that the behavior occurred.

Update copied project rules that combine the three design reviews or automatically advance after a proposal is accepted. Advance when Human authorization covers the next stage and its effects. Interpret the actual request and reply: accepting an Acceptance plan does not authorize implementation preparation merely because the Agent announced it would do that next. Existing explicit authority covering the relevant stages or effects remains valid, and completed stages need not be repeated. Review before beginning realization is a transition boundary, not an extra stage.

Implementation preparation should produce a clear execution plan, as linear as practical. A draft can expose missing design facts through rehearsal, but route-deciding experiments, research, and factual confirmation must return to investigation and design before the plan is ready to execute. They must not remain implementation steps that decide what to build. Ordinary implementation observations and repair remain part of realizing the agreed solution; failed material premises reopen only the affected design and dependent work.

Keep a linear plan in the Packet for ordinary work. When work qualifies for a Task Map, carry over each independent Track and its plan, and identify where Tracks must converge. Fold former Phase, Cell, and Slice structure into those plans while preserving dependencies and pending commitments. Apply the [Task Map guidance](../svc-task-packet/references/planning.md) to active Packets.

A full v17 installation includes the seventh Skill, `svc-writing`. With a v17-compatible CLI, install that missing Skill explicitly before updating a complete v16 set. For a partial installation, update the installed Skills by name and install only the additional ones you want. Review and update standing instructions and pointers after the file update. The `skills adopt` plan can refresh the pointers it manages. Review Consumer-authored instructions against the root instruction asset.

Check the changed boundaries with a non-trivial new capability request, a proposal accepted without next-stage authorization, an explicitly authorized continuation, and a draft plan whose experiment would determine the Technical route. Observe actual review objects, tools, and Agent assignments: the Agent should pursue the current stage result, respect the approval's actual scope, reuse existing authority, and resolve the design premise before presenting an execution-ready plan. Technical fact-finding may still serve a Product proposal, and an established iterative agreement retains its rhythm. Compare old and new guidance under the same host and Consumer instructions; success after adding extra stage rules to Consumer instructions is not evidence that the Skill revision itself repaired the behavior. Static source checks and prompted walkthroughs do not establish reliable automatic triggering or actual execution.
