# Feedback

Read this reference when arranging feedback for implementation, deciding whether a test-first loop fits, responding to a mismatch, reusing prior evidence, or changing a check or criterion. Return the next coherent change and the feedback that can distinguish progress, or explain which product, design, observation, or authority decision remains open. This expands the [Verification Skill](../SKILL.md); use this reference directly when its pressure is already known.

Feedback is part of the implementation search, not a report added after it. An over-weak oracle lets candidates satisfy an easier proxy; an over-specific oracle rejects valid implementations; stale state, noise, and delayed results can steer the search away from a correct candidate. Feedback value therefore includes semantic fidelity, resource and environment cost, timing, diagnosis, maintenance, false decisions, and the cost of unnecessarily restricting implementation space.

When the behavior is stable enough to state and the agent knows what should be true more clearly than how to realize it, a test-first loop can establish a useful boundary:

```text
stable behavior → check expected to fail for its absence → coherent implementation change → feedback → improve implementation while preserving the behavior
```

Red matters because it shows that the check can detect the intended absence or violation; an arbitrary failure, syntax error, or unavailable environment is not meaningful Red. Green means only that the executed check passed; it supports the behavior claim only when the oracle and observation mechanism are applicable to that claim. Refactoring searches for a better implementation inside the same behavioral solution space. If the product behavior is still being discovered, first obtain product feedback or build a disposable experiment; executable detail can otherwise turn an accidental interaction sequence into a permanent requirement. Test-first is a method under these conditions, not a universal ritual.

The feedback loop should use the smallest coherent change that preserves known product constraints and system invariants. A fast loop narrows an implementation or diagnosis question with cheap, timely evidence. A broader loop checks composition, the connected product result, or realistic conditions. The boundary is chosen by the current uncertainty and cost, not by tool labels; a repeatable performance benchmark may be fast feedback, while a nominally local check may be too slow or too weak. A later check should not be used as permission to break a known invariant temporarily.

When a mismatch appears, classify the next observation by what could explain it. A clear behavioral violation calls for implementation repair and requalification. An observation that adds an unstated implementation restriction calls for an oracle or observation repair. Invalid setup calls for corrected conditions. Missing discrimination calls for a new observation that separates the competing explanations. Evidence that the requirement no longer serves the product goal calls for Product or Technical reconsideration. These are directions for reasoning, not a mandatory triage form.

A defect can improve the behavior model rather than merely add a historical example. Ask what property, invariant, contract, state, or condition the counterexample revealed, then strengthen the general check when it reliably preserves that discrimination. Keep the concrete case when its rare history, important journey, or diagnostic value cannot be reached reliably by the general check. Reuse prior evidence only after checking the consumer connection and every changed requirement, implementation, input, state, oracle, environment, dependency, and observation assumption that matters to the claim; a new commit alone does not determine validity, and identical source does not establish identical runtime conditions.

Changing a test, threshold, fixture, generator, or observation needs a reason: the product requirement changed, its interpretation was corrected, or the mechanism needs more faithful observation or condition selection. Preserve the old discrepancy and qualify the revised check's sensitivity and scope when the decision matters. Do not weaken a criterion just because the candidate fails it, and do not retain a misleading criterion merely because it has always been green. A replacement is worthwhile only when it preserves the meaningful discrimination at a lower total cost.

Production feedback can reveal workloads, data, and use conditions absent from development, but observation there may already affect users. Match automation's permitted decision to evidence credibility, exposure, recovery or compensation, and the consequence of error; code rollback cannot retract a sent message, charge, or disclosure. Feed observed gaps back to the owner of the behavior, requirement, design, or observation mechanism, while retaining Human judgment for preference and perception that no trustworthy oracle can replace.
