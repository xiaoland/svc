# Agent 工作方式与人机协作方案

状态：用户已授权实施，随后明确修订：svc-methods 升级为 svc-workflow，svc-verification 保持独立，按名称发现。最终为六入口，共同归入未发布的15.0.0。以下原合并细节作为已经实施过的设计记录，被本段与末尾修订覆盖，不作为当前源合同。

## 目的与结构

Agent 需要把人的目的、当前承诺、工程行动和结果反馈连接起来。单列方法能帮助局部求解，却不能充分说明何时向人提出方案、何时自主实施、怎样消费人的体验反馈，以及反馈推翻旧前提后怎样继续工作。新 Skill 所有这些人机协作关系及完成工作的共通方法，让人能够掌握方向和关键取舍，让 Agent 对工程推进和可支持的结果负责。

工作流程决定承诺、确认和反馈怎样发生；方法解决当前缺口；Task Packet 保存可恢复的工作状态。这三个层次不等于阶段、角色或必须依次调用的入口。采用阶段确认式或持续迭代式，不要求用户理解方法内部词汇或维护一份流程配置。

所有方式共用以下原则：理解人的用意而非机械照抄措辞；区分目标、偏好、提案、事实与授权；对事实和工程方案独立判断；在既有授权内解决常规问题；把需要人的决定整理成有依据的建议；完成 Agent 可以完成的验证；用明确的残余说明尚未建立的结果。用户列举的对象可能用于指向一个尚未准确命名的概念，例子不能自动成为穷尽需求或固定实现。

验证基础仍是产品目的、行为要求、观测与 oracle 保持联系。oracle 对需求关心的行为变化敏感，对保留相关需求的实现变化不敏感。反馈不仅检查代码，也可能暴露需求、设计、条件或判据的问题；通过检查与得到人的接受仍是不同结论。

## 两种协作流程

| 关系 | 阶段确认式（瀑布式） | 持续迭代式（敏捷式） |
| --- | --- | --- |
| 当前承诺 | 收敛当前阶段的目标、范围、关键方案和判断依据后，按已经确认且获准的承诺推进 | 在共享目标和授权边界内持续修订当前实施范围与路线，不把开始实施当成需求冻结 |
| 与人确认 | 在有实质承诺变化的阶段边界呈现可审阅结果；已有授权内的常规步骤无需重复确认 | 在产品决定、范围取舍或新授权需要人时确认；日常工程与已授权迭代自主推进 |
| 新反馈 | 判断是否改变已确认前提；变化时标明影响，暂停依赖失效前提的工作，重开受影响的承诺 | 把反馈纳入当前理解与计划；关键矛盾可局部暂停以重新设计，再继续迭代 |
| 反馈交付 | 按当前阶段的消费需要返回方案、实现或验证结果；不把阶段通过等同整体完成 | 交付可消费的变化与其证据、体验入口和剩余问题，让体验反馈继续影响下一段工作 |

反馈若只是揭示既定行为尚未实现，应在既有授权内直接修复，不因来自用户就重开产品决定。只有改变实质要求、关键方案或授权边界时，才重新收敛受影响的承诺。持续迭代式也不将每条反馈自动提升为已经决定的新需求。

阶段确认式的典型路径是共同理解目标，形成可审阅的方案与判断依据，确认当前实施范围并建立授权，实施与反馈，再判断结果和剩余义务。它允许调查、设计、验证在每段递归出现，不要求先完成整个项目的设计，也不强制每个任务新增相同文档。

持续迭代式的典型路径是恢复目标、反馈与当前授权，厘清下一段产品和工程问题，形成足够连贯的方案，实施并取得产品相关证据，交付体验，再按反馈更新需求、方案和计划。一次迭代可以只完成调查或设计，不以快速写代码定义敏捷，也不引入固定 sprint、backlog 或会议制度。

确认方案不自动授予所有操作权限；“继续研究”不等于“可以修改源码”。反过来，已经明确授权的实施不必因为阶段结束或新的方法调用再询问同一权限。自由提交、安装、发布、真实账户操作等授权分别来自实际项目和用户，不能由流程名称推导。

项目约定或人的直接指令优先。没有明确模式时，依据当前协作约定与请求识别工作方式；若区别会改变下一项实质行动，先说明建议与影响再请人决定，否则推进共同允许的调查和方案工作。不要默认为未确认变化已经获准。局部重大问题停下核对设计不等于项目切换流程；改变整体确认节奏需要保持与人的共同理解。

## 共通方法与所有权

| 方法 | 触发缺口与返回 | 内容边界 |
| --- | --- | --- |
| Explore | 下一项决定依赖非显然信息，返回支持当前决定的答案及残余 | 按定位、理解、解释、预测、比较等信息目的选择来源与判别动作；明显权威查询直接执行 |
| Design | 产品或技术安排尚不连贯，返回当前消费者足以使用的方案 | 产品设计、技术设计、验证设计是同一方案的视角，不是三个必经阶段 |
| Planning | 不清楚下一段做什么、依赖谁或何时重新判断，返回有限前瞻的可执行路线 | 说明动作为何排序、推进到何处、什么反馈会改变路线；不复制 Packet 的拓扑术语和存储规范 |
| Implementation | 需要实现已授权变化，返回实际效果、反馈和残余 | 包含必要局部调查、修复和验证；发现方案或权限矛盾时回到对应问题 |
| V&V | 当前判断缺乏可靠依据或反馈误导，返回证据支持的结论、条件和局限 | 解释 requirements/oracles、条件选择、证据取得与复用、反馈及纠偏，不降为末尾测试 |

验证设计聚焦“应判断什么、怎样观测、如何形成判据、需要什么可验证边界”，放在 Design 的一个有实际检索用途的参考中。oracle 原则及判断依据的专题深度由 V&V 参考唯一所有，验证设计引用它；不再另写一份原则。V&V 方法同时服务设计、实施、验收与既有证据复用。

Task Packet 继续所有每个非平凡任务的持久状态、计划拓扑、信息模块及关闭规则；Workflow 的 Planning 所有推导和调整路线的方法。Specs 所有长期知识，Taste 所有有后果的设计与实施判断，Agent Collaboration 所有 A2A。Workflow 只保留其独立使用所需的最低边界及按需发现入口，不搬入其它 Skill 的专门合同。

## 内容与加载

建议入口为 `corpus/svc-workflow/SKILL.md`，包含目的与原因、共通责任与 V&V 基础、当前工作的首动作、两种协作流程选择、五种方法的触发和返回，以及完成或受阻的边界。参考正文按 semantic paragraph 换行。

`references/staged-collaboration.md` 与 `references/iterative-collaboration.md` 分别展开两种流程，用实际交互说明阶段承诺或持续反馈怎样影响下一步，而不复制共通原则。

保留现有 `explore.md`、`design.md`、`product-design.md`、`technical-design.md`、`implementation.md`；新增 `planning.md` 与 `verification-design.md`。现有 Verification 入口迁为 `verification.md` 方法参考，现有 `requirements-and-oracles.md`、`evidence.md`、`feedback.md` 迁入同一个 references 目录，保持条件触发和语义所有权。不增加默认模板、流程状态机、角色层、方法配置或安装依赖。

Skill 描述必须同时覆盖软件任务的组织与人机协作，以及调查、设计、计划、实现、判据或反馈缺口；不只写“选择工作流”，否则用户直接提出验证问题时可能发现不了合并入口。入口可直接进入匹配的方法，已明确工作方式的任务无需反复加载两份流程。普通查询与机械动作保留直接路径。拓宽描述会增加入口匹配面，但合并消除了 Methods/V&V 之间的跨 Skill 检索；机械检查无法证明宿主可靠触发。

## 交互走读与限制

以下走读检查的是指导是否能导出有意义的下一步，不是实际 Agent 性能测试。

1. **只授权规划。** 两种方式都继续调查、设计和更新 Packet，形成可审阅结果；不能因为敏捷而改源码。当前 SVC 任务就是这个实例。
2. **实施中反馈推翻产品前提。** 两种方式都停止依赖失效前提的动作并核对影响；阶段确认式明确重开已确认承诺，持续迭代式修订当前需求与路线。二者都可先完成独立已授权部分，也都不能把用户疑问自动当成全部设计已确定。
3. **人暂时不能验收。** 返回可体验状态、已有证据和未验收项，继续独立已授权工作；既不把沉默当作接受，也不把所有工作冻结至用户回来。
4. **检查通过，用户路径仍失败。** 自行在合理可用边界复现，核对 oracle、条件、观测与产品要求，修正证据或方案；不能把所有产品验证推给用户，也不能以此前合成检查通过拒绝反馈。
5. **局部机械修复。** 直接修复并取得适当反馈，不制造阶段审批、两份流程阅读或一套设计材料；非平凡任务的 Packet 规则仍保留。
6. **反馈是建议或信息而非新增授权。** 判断其实际目的、变化范围与授权关系；事实判断独立核对，人的产品取舍形成可审阅建议；新效果超出授权才需决定。不能将每条新反馈都变成默认写权限，也不能把已经授权的修复反复升级为审批。

依据包括 Velune 指定会话的实际循环与本会话的方案确认模式，尚未证明 Skill 的真实发现、加载或执行效果。实现后检查可搬运性、导航与交互逻辑；未来真实使用产生的可定位缺口才驱动进一步调整，不新增 Corpus 自动化测试或模拟 Agent 测试设施。

## 落地顺序与分发范围

第一步在同一个源变更中合并 Skill，修正所有权与加载导航，删除两个旧入口及重复原则，并同步其它 Skill 的条件引用。所有新内容必须在新目录内自包含，不依赖 root index 或兄弟入口。保留刚收敛的 V&V 语义与既有其它任务修改。

第二步同步五入口合同：仓库 Skill 检查集合、CLI 安装默认与归档验证集合、adoption 发现集合、归档错误说明，以及许可证和版本准备说明、框架导航、用户手册和开发指引。不改变 archive/record/result schema，不新增 Skill 注册框架，不把正文带回 CLI；没有证据需要改变当前事务机制。

第三步解释未发布 v15 草稿安装的入口整理：准备新目标与确认新入口可安装，按原管理器检查并移除旧 Methods/Verification（以及更早 sub-agents 草稿），安装 Workflow，更新其余实际安装项，刷新各项目 adoption 与自定义指针。保留修改文件和第三方锁记录的所有权保护。CLI 不用别名、自动跨名迁移或转发 Skill 掩盖新边界；当前原始名的记录检查和移除仍有用途。第三方管理器消费同一个独立源目录，工作流内容不承担安装职责。

迁移指导优先更新已有 agent-skills 总览与 agent-collaboration 草稿整理说明中受五入口影响的文字；是否新增专门 working-guidance 指导取决于两项旧入口替换的内容能否在总览中清楚表达，不默认再建文档。历史任务记录保留已发生事实，不全文替换旧名。

第四步做按比例验证：检查独立 Skill 路径、锚点、元数据与许可，搜索现行旧名指针，走读上面的交互，执行 CLI 行为回归和全量现有检查。CLI 测试保留真实文件所有权、计划过期、归档当前集合与 adoption 刷新的边界，仅因名称变化更新当前集合 fixture；不为每个新段落写内容断言。不因已有三处当前名集合就顺手重构成共享 registry，CLI 与 Corpus 的独立边界保持。

## 最新边界修订

用户决定保持独立svc-verification。Workflow仍所有人机协作方式及Explore、Design、Planning、Implementation，并保留足以独立工作和协调验证设计的最小责任；专业V&V入口与requirements-and-oracles、evidence、feedback三份参考归Verification。通过Skill名称按需发现，不设必需兄弟路径、父级依赖或安装依赖。Workflow的Verification Design保留本地设计协调，专题深度指向名称。默认安装、归档校验、adoption、CI及现行导航改为六入口；Verification是当前可安装、更新、采用的名称，而非退休名。旧Methods仍无别名并可按原记录显式检查移除。先前五入口和二旧名移除指导相应撤回。不得因本调整升版本或扩展到未授权的测试自审修复。
