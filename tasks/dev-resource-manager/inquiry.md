# 开发资源需求调查

## 调查问题

这四个真实项目中，开发者实际需要观察、访问或控制什么资源？现有控制通过谁执行，哪些动作可重复执行，哪些有共享、系统权限、持久数据或外部服务边界？这些差异是否支持按控制特性分类，而不引入任务语义？

本次观察时间为 2026-10-27，以当前本地文件为依据。文档说明意图，配置和控制代码说明当前实现；两者冲突时保留差异。没有启动或探测运行时，因此不报告资源当前在线、配置实际可用或用户操作频率。

## 项目证据

| 项目记录 | 本轮解决的区别 |
| --- | --- |
| [InKCre](inquiry/inkcre.md) | 复合 runtime、跨仓引用、运行位置与访问通路、停止即销毁数据、现有脚本的作用范围 |
| [Velune](inquiry/velune.md) | 可选遥测、远端接收端与隧道、隔离应用实例、设备转发、观察新鲜度、项目接入约束 |
| [nearby-audio](inquiry/nearby-audio.md) | 主机级唯一安装、系统服务与驱动、签名和设备安装、需人工完成的浏览器集成 |
| [bl-gallery](inquiry/bl-gallery.md) | 同仓多入口、持久数据、等待在途请求的停止、有限业务作业与资源生命周期分离 |

表内差异都已由具体配置或控制代码交叉核对；记录中的编号用于连接下述判断与来源。

## 已确定的判断边界

用户确认资源管理与 App／CLI 产品边界，拒绝让 SVC Dev 推断任务或开发工作语义，并在本轮调查返回后同意继续收敛。已确认的产品语言现由 [产品文档](../../docs/prd/development.md) 拥有；下文保留其证据推导。上一轮“工作准备、并行开发、收尾”的假想旅程不作为需求依据。

不能把项目配置中的引用写成当前使用证明，不能把可观察写成可控制，不能把资源停止写成数据清理，也不能把发现项目脚本当成执行授权。

## 综合判断：按控制特性分类，但不压成单一类别

以下分类由本轮项目证据推导，用户同意后已进入产品文档。分类不是五种已实现的资源类型；本轮产品需求复查与收口提案由 [Design](design.md) 拥有。

| 控制特性 | 真实依据 | 必须保留的区别 |
| --- | --- | --- |
| 观察与访问 | InKCre external 引用、Grafana 入口、各 Web UI | 能访问不等于能停止；观察有来源、时间和身份，不能把配置存在当作资源就绪。 |
| 运行控制 | Vite、Hono、Inbox、LGTM、系统服务 | 启停动作应由项目或系统管理入口执行；Inbox 需要等待在途工作，LGTM stop 保留数据。 |
| 供应与销毁 | InKCre worktree Compose runtime | 创建实例、初始化数据、删除卷与普通启停不同；当前 database stop 实际带数据删除效果。 |
| 连接控制 | SSH control tunnel、ADB reverse、外接 runtime | 建立／断开通路不等于启动／停止远端资源；引用关系和实时使用关系不能混淆。 |
| 安装与更新 | 原生 App、设备安装、HAL 驱动、浏览器扩展 | 构建产物、已安装版本、运行实例与系统许可分开；部分步骤需要系统授权或人工完成。 |

同一资源可以同时具备多项特性。同一实例在不同调用方处也可能具有不同的有效动作：InKCre owner 能销毁数据库，attached client 被明确禁止。把“受管／外部／手动”当作资源固有且互斥的类型，会丢失这个差异。

因此建议让资源登记和公开结果至少能表达三个相互独立的问题：这个入口支持什么动作；实际控制者是谁、当前调用者能够请求什么；动作影响哪些实例、连接、持久数据或主机组件。尚不决定具体 schema，也不要求把每个底层进程都暴露成独立资源。

## 已由证据支持的产品要求

1. **资源身份独立于展示入口。** InKCre I1／I3 是跨仓引用同一 owner runtime 的实际合同；nearby-audio N1 是多工作树不能各自拥有独立安装的反例。项目路径是来源信息，不足以决定实例身份和控制范围。
2. **动作名称不能掩盖效果。** InKCre I2 的 stop 会删卷，Velune V2 的 stop 保留卷，bl-gallery B4 的 stop 等待在途请求。SVC 当前 exec／manual／absent 描述执行方式，不能独自承担这些区别。动作效果必须由可信声明／控制者提供，不靠解析命令名猜测。
3. **资源状态可以有多个独立方面。** Velune V2／V4 的后端运行、隧道连通、设备转发各自变化；nearby-audio N3／N5 的已构建、已安装、已加载、已授权也不同。界面可以保持简洁，但不能用一个绿灯隐藏尚未观察或尚未完成的方面。
4. **现有控制者继续拥有语义。** InKCre 的 Compose provider、声邻的系统服务和 Inbox 的 Worker 已有明确控制合同。SVC 负责发现／登记后提供一致的查询和请求入口，不另建数据库清理规则、音频授权规则或分类任务队列。
5. **观察和管理可以分步接入。** InKCre I6 证明存在未声明的现成资源；Velune V7 明确不接受项目内引入 SVC。这证明项目接入有成本，不证明必须提供项目外登记。用户质疑其 ROI 后，本轮方案采用项目声明复用既有脚本，允许仅观察或人工控制；不承诺纳管未接入项目。现有 `network_scope=remote`、host 共享范围及脚本调用已经允许项目管理外部运行资源，不能把资源运行位置与声明来源混为一谈。
6. **仅使用显式资源关系。** 可采用声明、代理配置、owner descriptor 或已有控制脚本证明的关系。Velune V3 证明有可选资源；不能因为存在关联就自动形成强依赖或启动整个资源集合，更不能从任务描述推断该集合。

## 对上一轮提案的修正

保留资源及实例、App／CLI 一致语义、观察与控制分离、数据保护、共享引用这些方向。移除以“正在做什么开发工作”为核心的组织方式，也不继续使用虚构的两工作树旅程作为需求依据。

“准备环境”“清理不用的资源”和依赖自动编排不再作为已经确定的近期功能。已有的资源供应或项目明确组合命令仍是调查对象，但自动判断需要哪些资源、某资源是否无人使用、是否可以销毁，都没有获得本轮证据支持。完整管理窗口也仍是候选交互形态，本轮没有进行界面取舍。

构建、分类、导出和测试是有界动作，不能因它们使用资源就全部纳入 SVC Dev 的作业管理。原生构建可以是现有安装动作的准备步骤；分类内容、Agent 会话和音频协同保留在各项目自身产品中。

## 仍需解决的问题与证据边界

- 用户已确认 [Design](design.md) 的技术取舍并授权验收设计；项目外登记不作为前提，也不通过新增存储层变相实现。[Verification](verification.md) 连接本调查的四类实际区别与判据，真实四项目的运行状态及接入结果仍未验证。实现准备仍待后续阶段授权。
- 四个项目存在真实配置与脚本，但本轮没有统计日常操作频率，不能据此给所有资源类型排优先级。
- 未运行 probe、启动／停止服务、连接远端、操作设备或调用模型；不能声称资源当前在线、脚本成功或多平台行为已验收。
- InKCre、Velune、bl-gallery 有未提交修改；来源是读取时的工作树。Velune 历史 Host 和部署记录的过时阶段文字已单独标记，不作为当前能力依据。
- 自动发现、共享实例合并、实时使用证明和安全自动清理均未验证。它们不作为默认为真或必做的前提。
