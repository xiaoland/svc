# V&V 的理解与内容依据

本任务仍处于共同收敛方案阶段。已写 Corpus 内容及 16.1.1 版本准备是未采纳草稿，不能以机械检查通过证明方案有效。本轮仅重整任务材料，不修改或提交 Skill。用户并列的“出发点、元理论、元认知”指向整体理解，不是三个待分别定义的交付项。

依据是 [会话总结](../../../factory26/tasks/verification-system.md) 及原存档 T03、T05–T10、T11–T18 的相关论证。已核对全部用户消息并定向读取关键助手回复，不声称通读全部原始消息。factory26 后续研究材料辅助定位，不替代原会话或当前用户授权。以下是根据材料形成的解释，不倒写为用户逐项批准的理论。

## 从产品目的理解验证

实现是达到产品目的的一种手段。修改软件时，我们需要分辨：哪些变化使目标更接近，哪些破坏了必须成立的行为，哪些仅改变实现形式。代码、构建和检查成功都可能相关，却不是这些问题的答案本身。V&V 要建立可被检验的判断依据，使实现变化能够受到产品目标与实际行为的反馈，而不是仅适应当前检查。

产品意图、对要求的表达、实现、观察和成功判断之间存在联系，但不是同一个东西。把自己的理解写成规格，再按同一理解生成实现和测试，三者一致也可能只是共享了误解。Verification 判断是否符合表达出的要求；validation 还要考察这套要求及结果是否服务实际目标。后者不是最后一句接受表态，前者也不是没有价值：没有足够稳定的要求，迭代会失去可依赖的约束；不允许检查这些要求的理解，又可能稳定地维护错误方向。

因此，规格既提供当前判断的依据，也需要对新的产品认识负责。已明确的合同、对合同的解释、实现假设和偶然细节有不同地位。允许修正规格不意味着候选做不到就可以放宽；保持规格稳定也不意味着永远冻结一个已被证据指出的表达错误。

## 从这个理解推到 Oracle 和证据

如果两种实现在相关条件下都满足同一要求，Oracle 不应仅因表示不同而改变判断；如果相关要求被破坏，它应有能力识别。因此“对需求相关差异有辨别力，对保持要求成立的实现变化保持判断不变”有明确来由：判据需要反映我们真正要保持的差别，而不是当前实现的形状。明文接口、时限或实现约束若本身属于要求，就仍是相关差别。

“保存后下次登录仍可使用该设置”约束跨会话行为。某次 URL 跳转或成功提示与它没有必然关系：可以出现提示却没有持久化，也可以改变页面路径而持久化仍成立。这两个反例分别揭示接受范围过宽和过窄。观察工具可以依赖 DOM、API 或文件，但这些机制当前能读到的内容不能自行定义预期。用语义 helper 命名也不能建立这种关系，需要解释它实际观察了什么。

一般性质有价值，是因为它表达哪些行为必须成立，并允许满足要求的不同实现。排序丢失重复元素可以揭示“输出保留输入多重集合”的性质，而非只留下固定输入的答案。但性质不是全部要求，也不是对全部条件的证明。排序还可能有顺序、稳定性或性能要求，生成器也可能不到达某种罕见状态。反例可能说明遗漏了性质，也可能只是已有性质未被实现、未被触发或未被观察；不能把每个故障都归为规格缺口。

正确判据仍需接触有关事实。输入、状态、历史、并发和故障条件决定实际经历什么；观察机制决定哪些结果进入判断。等价类和边界有价值，是因为我们依据行为规则划分不同情况并挑战容易混淆的交界；状态历史有价值，是因为同一动作的含义可能随先前操作变化。每个选择都带着对未选情况的假设，不能靠技术名称或覆盖数字消除盲区。

真实结果可以挑战中间信号无法检验的假设。SMTP 接受与实际收件回答不同问题；真实数据库与假设正常工作的 repository mock 提供不同事实。但真实来源也不能自动使所选指标充分。更大边界应保留重要语义并增加相关证据；更小边界适合密集检查可在那里成立的性质。互补证据不是同一断言重复几遍，也不由层级或 Agent 身份天然产生独立性。

## 从证据理解持续迭代

反馈会改变下一次实现搜索，所以它的偏差有行动后果。过弱判据鼓励满足代理目标，过具体判据冻结合理实现，状态污染或噪声可能使正确候选被修改；迟反馈让更多变化积累后才发现差异。反馈价值因此包含可信度、取得时机、诊断能力和维护成本，而不仅是一次执行是否通过。

行为已经足够明确时，可以先把下一块稳定约束表达成能产生反馈的检查，再让实现满足它。Red 的理由是确认对预期缺失敏感；Green 是这些条件下的当前结果；Refactor 是保持约束而改善实现。产品行为尚不明确时，先固化操作步骤可能冻结尚未理解的设计，应通过原型和真实反馈形成稳定认识。TDD 的价值取决于先表达了什么，不来自顺序仪式。

快反馈帮助缩小当前搜索和诊断范围；整体结果检查判断这些局部变化是否组合成立。使用频率取决于当前问题与取得证据的成本，性能 benchmark 也可能是快反馈。每次变化应足够连贯以保持已知关键约束，不能用更小的代码修改量解释暂时破坏一致性。全局设计问题和固定切片方法在原会话中仍有未验证部分，不据此增加治理层。

生产观察把实验未充分涵盖的现实条件送回认识与实现，但获取信息时也可能已经造成损失。自动响应的后果、暴露范围和恢复能力必须与判断可靠性相称；回滚代码不能撤销已经发生的外部效果。这个限制不等于 V&V 要自行接管发布平台或审批制度。

## 用一个完整情境检查理解

假设要求明确为：“用户保存一个不同于初值的设置，结束会话并再次登录后，可以看到和使用新值。”第一次检查只看保存提示，这个检查应被无持久化的候选反驳；第二个候选只改路由而保留行为，不应被旧 URL 判据拒绝。改成实际保存、跨会话读取并使用新值后，检查与要求建立了更强关系，但只支持实际观察过的条件。

若担忧不同用户隔离、故障时丢值或并发更新，须先找到要求或当前风险依据，再选择相关条件，不能把“更全面”变成擅自添加产品规则。局部保存规则可用便宜性质获得快反馈；真实存储验证持久化假设；产品路径判断是否通过真实入口完成承诺。这些结果支持不同结论，也帮助缩小差异原因。

若结果稳定通过，而用户仍找不到保存入口，可能说明最初的持久化要求不足以承载实际目标。这时不能靠增加存储断言修复理解，需要回到实际使用问题；这个反例提醒我们不能把 V&V 全部化约为忠实执行一份既有规格。

是否保留某检查、用什么边界、何时执行，都由其语义与反馈价值决定。临时改变 locator 可以修复观察机制；把本来应持久化的值改成“不需要持久化”，则改变接受条件。它们不能因都叫“改测试”而同样处理。

一个检验过强解释的边界是已有可信证明的、输入域明确的排序函数。若当前任务只需保持该已确定的语义，不必为了“持续反馈”重新进行产品探索或增加 E2E。行动所需的是有根据且可被挑战的判断；运行实验是取得依据的重要方式，但不是所有任务的必经仪式。现有静态约束、证明或已资格化模块保证可以拥有相应结论，消费者仍须检查适用条件与连接。

## 对后续内容设计的约束

需要让读者能够从这套理解推断新情境中的选择，不能仅复述原则或执行提醒。Oracle、性质、条件选择、真实交互、成本与反馈不是独立口号；每项方法都应在它补足的认识或行动缺口出现时引入，并保留不能推出的结论。

保留有用材料，删除或移走无法改变当前判断的重复和制度性旁支；必要的解释不能为短而省略。是否继续四分支、增加基础章节或合并引用，尚不作为结论。前述完整情境是推理检验，不是运行产品、模型自动采用或方法有效性的实验证据。
