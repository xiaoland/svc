# 目标 svc-verification

状态：用户已认可本方案并于 2026-10-06 授权实施，未授权提交或发布。用户所称 svc-v 按当前 Skill 身份 svc-verification 理解，本方案不包含重命名决定。认识依据见 [Inquiry](inquiry.md)。

目标是帮助 Agent 建立、使用和改进产品迭代所依赖的判断依据，使实现可以变化，产品要求与现实反馈持续约束这种变化。检查修复与完成声明是其中的应用，不再作为全部定义。

## 入口承载的理解与行动

SKILL.md 必须自包含一段能指导判断的完整解释：产品是目的，实现是满足目的的一种安排；规格和检查让目的能够指导行动，却都是可能有错的表达。当前机制接受了当前表现，不等于已经正确理解并满足产品目标。V&V 分别判断符合表达出的要求，以及这些要求和结果是否服务实际需要。

从这个关系解释 Oracle 的双向辨别、证据的条件和范围，以及反馈怎样影响实现搜索；不把它们变成术语清单。用一个足够短的产品例子连接判据接受过宽与过窄的问题，不另设必读理论总览。

入口也应给出立即可用的行动：辨认当前要决定什么、已有依据和关键缺口，使用适用机制或取得能改变判断的观察，再解释结果、限度和下一步。已存在明确且适用的检查时直接执行解释，不因使用 Skill 而新增文档、测试或设计交接。这是局部判断关系，不是每项任务必须从头走完的阶段流程。

description 覆盖正常改动需要可靠反馈、全绿仍未达到目标、检查阻碍合法重构、反馈过慢或不可信，以及已有证据能否继续使用。只保留独立使用必需的权限、Task Packet 与返回边界，避免通用声明淹没 V&V 内容。

## 按需内容及其关系

推荐当前目录为 SKILL.md、LICENSE 和以下三个 reference；文件名为暂定载体，不是新术语。

| 入口问题 | 文件 | 该次阅读应足以完成的判断 |
| --- | --- | --- |
| 我们究竟在判断什么算对？ | references/requirements-and-oracles.md | 形成或修正忠实于要求、容纳合法实现的判定依据 |
| 怎样取得足以回答问题的证据？ | references/evidence.md | 选择、执行并解释可信观察，知道它支持什么、尚缺什么 |
| 怎样让反馈持续改善实现？ | references/feedback.md | 安排和调整实现搜索、整体检查与证据演进 |

第一篇从目的、要求表达和设计假设的不同地位出发，解释为什么实现不能自行定义预期。用性质、不变量、状态、过程或量化表现刻画所关心的差别，再说明如何找到可观察表现和 Oracle；双向反例检验这些表达的联系。性质与案例的价值和边界在此形成基本理解。

第二篇从“正确判据尚不知道系统经历了什么、观察到了什么”出发，解释条件选择、观察机制和可信假设。讨论等价类与边界、状态历史、组合、生成输入和故障条件的选择依据及盲区；真实依赖、替代品和局部/真实组合/产品结果提供什么不同证据；怎样构造、观察、重置、复现与测量。选择每个观察时就说明其结论范围、验收与诊断价值、原始失败和未观察行为。已有保证和证据的复用按适用条件判断。

第三篇从“反馈不仅传递结果，也改变下一轮搜索”出发，解释 specification-first 的适用条件与有意义的 Red，快反馈与整体结果的互补，总成本和最小连贯变化。说明如何把差异返回实现、规格、设计或观察机制，以及反例如何改善性质或条件模型、什么时候保留具体案例。真实运行回流、自动响应的后果及判据演进依据在相关处展开，不由此扩建发布治理。

合并结果解释与证据取得是因为两者共享一个判断：这项观察为什么足以回答问题、允许何种结论。先读设计、再读解释才能完成这个判断，会增加往返和重复。根据结果改变下一轮工作的内容进入第三篇。若将来某部分出现独立内容与读取压力再拆，不为固定数量牺牲理解完整性。

## 展开与边界

正文以问题的推导展开方法，不固定“what/why/how”段落模板。例如 mock 的论证起于依赖行为是否被当成未检验前提，再解释真实交互与替代的适用条件；TDD 的论证起于对行为是否比对实现更有把握，再说明先形成反馈约束如何影响搜索。

可用保存设置/重启导出的贯穿例帮助理解，也保留排序、权限和测量的专门反例。每个例子只承担它能解释的关系，场景细节不升级为普遍要求。理论解释不替代动作，动作条款不能代替理解；必要理由不能为了精简删去，重复的正确句子也不因“没错”而保留。

V&V 专门知识由本 Skill 自包含；Methods 维护通用 Explore/Design/Implementation 并按压力发现本 Skill。当前 Test Design 的专业内容据此归并，避免运行 V&V 前必须安装 Methods。问题实际扩大为产品选择、未知机制调查或系统改造时，可发现相应 Skill 获取补充指导，但缺口与当前可继续动作仍在此说清。

本方案不规定全量 TDD、固定测试比例、强制 E2E、必建 assurance plan 或新增 Corpus 测试。已有可信静态保证足以支持当前决定时可以复用，不把反复运行实验当作仪式。

内容质量以迁移判断能力审阅：遇到新问题，读者是否能说明当前检查为何值得相信、为何不足或为何妨碍改进，并据此选择动作。文件闭合、读取路径和术语复述不证明效果。真实 Agent 采用和运行收益仍需后续实际使用观察。
