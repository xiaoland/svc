# 机器压力与执行管理

## 当前结果与权限

2026-10-28，用户提出新能力：让 Agent 获知当前机器资源压力并自行调整执行，让人能自行终止任务；接受讨论 SVC Dev 从开发服务器／资源扩展到通用 run／task。随后明确同意产品提案，并要求“你自行主动继续收敛，交付一个版本给我看看”。这次指令覆盖后续技术、验收、准备、实施及本机交付，无需逐阶段复核；公开发布不在本轮范围内。沿用禁止新增自动化测试、允许脚本，以及自由提交和本机开发签名安装的授权。

目标是减少 Agent 执行对日常使用的干扰，并使人能找到、理解和终止具体执行。压力可见不等于强制限额，自愿接入也不等于覆盖 Agent 的所有工具调用。只有实际覆盖并获得控制权的执行才可承诺终止。

## 已核对事实

[开发资源产品文档](../../docs/prd/development.md)将 SVC Dev 定位为人和 Agent 共用的开发资源管理能力，不由 CLI 命令树决定范围；当前明确排除通用作业管理，不推断开发任务目标。新需求会改变前一个范围限制，未要求改变后一个语义限制。

[run 产品文档](../../docs/prd/run.md)已有具名有限命令、同意图并发收敛、execution ID、输出跟随与结果查询；没有后台 runner、工作流图或就绪模型。[共享执行合同](../../docs/product-tdd/execution.md)规定 run／dev 共享机械执行，但分别拥有领域语义；历史 PID 不授予接管或终止权，也没有完整进程树控制保证。现有 dev 等待型动作不可中断，不能在 UI 中直接改成可取消。

[上一轮反馈](../dev-panel-ux/packet.md)记录用户实际感知的全系统性能下降，以及 Agent 同时运行观察宿主与构建的安排。没有证明唯一性能原因。那次已停止实验，但仅凭清理不能防止下一次类似执行；本任务讨论运行前及运行中的反馈与控制。

## 已接受的产品方向

SVC Dev 扩展为开发环境中的资源与执行管理。资源身份可持续存在，一次执行有独立身份、起止与结果。构建、验证、临时观察脚本可以作为执行被管理，不必伪装成服务；任务一词在本产品中只表示运行中的执行，不解析 Agent 的工作目标、Task Packet 或业务任务。

机器压力、当前执行和可用控制形成一个使用过程。人可先看到整机压力，再查看有来源依据的执行归属、活动和消耗，最后选择正确控制。不能归属的负载保持未归属，不能因某个命令与压力同时出现就断言其造成卡顿。项目和 Section 仍可用于导航；主机级入口要能暴露未归属项目的执行，不能只展示当前展开项目。

Agent 的程序化入口提供带时间、采样窗口及可用性说明的压力事实，并提供当前受管执行与可用控制。Agent 在启动高消耗工作之前和运行期间据此选择串行、推迟新任务、降低工具并发或结束自己可控的非必要执行。这是合作式调整，不承诺所有 Agent 一定读取，也不承诺仅降低优先级就能减轻内存压力。限额、自动排队和自动杀进程不是本提案的默认行为。

人可以看到执行来源、项目／工作目录、命令摘要、开始时间、状态、日志及可用控制。停止等待与停止执行必须分开。终止请求、控制者接受和进程实际退出也必须分开；中断后的产物或业务操作可能需要人工处理，不能把进程结束描述为回滚成功。已失去控制的执行不能显示为可可靠终止；已提交到外部控制者的操作与就绪后释放的服务沿用其明确控制入口。人主动终止需要作为明确事实回传给 Agent，不能当普通失败自动重试；结束一次命令不等于结束整个 Agent 会话，防止后续重新启动的约束与接入覆盖需要明确。

对显式受管执行提供正常停止，并为人需要紧急释放机器的情形提供独立的强制终止入口，明确对象、范围和可能遗留的状态。用户已同意这项产品提案；实现没有将旧资源动作的不可中断声明改为可强杀。终止必须针对执行身份及实际可验证的控制范围，不能按名称批量杀进程，也不能声称能消灭已逃离管理的全部子进程或远端工作。

保留项目声明以复用稳定命令，同时建议支持一次性的显式受管执行。后者只登记这一轮真实调用，不引入项目外持久资源目录，也不把每个临时诊断脚本都要求写进 svc.json。Agent 绕过该入口启动的工具是否能可靠发现、归属或控制仍待核实；可观察不等于可控制。外部进程接管不作为默认承诺。

App 面向人的压力概览、执行清单、详情与停止入口，CLI 提供同一能力的机器入口。CLI 的 run／dev 命令布局在技术方案阶段决定，不把产品范围等同于把 run 改名或嵌入 dev。

## 当前范围及判断依据

建议包含整机压力观察、受管执行的身份／状态／输出／消耗关联、人类停止与强制终止，以及 Agent 的查询和合作式调整。明确排除任务语义推断、工作流编排、缓存或构建系统、默认自动杀进程和未经控制权确认的全机接管。采集和展示本身必须有低开销边界，不能为监控增加高频扫描、重复构建或 GUI 观察宿主。

验收区分 Agent 能取得新鲜事实与 Agent 确实作出调整、人发出停止与实际工作停止、受管用量与未归属负载，以及工具可运行与工具没有明显额外干扰。下文记录了采样、控制和开销观察；没有承诺所有宿主自动接入，也没有通过人为制造系统压力证明整机体验。

## 技术、验收与实施路线

采用同一 CLI 的 `dev monitor` 提供主机压力及跨项目执行清单；`dev exec` 运行一次性命令，`dev terminate` 请求其实际 owner 终止。旧 `run`／dev 动作沿用原语义并只读呈现，没有控制通道就不提供终止。复用 ExecutionStore schema 2、日志和生命周期锁，一次性执行以 run/managed 区分；额外元数据只拥有标签、来源、采样身份与控制请求，不复制机械状态。

采样采用 psutil，提供短窗口 CPU、可用内存、磁盘读写速率和可验证的当前后代用量。macOS 内存压力另取系统等级，不能将内存占比伪装成内存压力。菜单栏沿用 420pt 面板：机器概览始终在上方，资源／执行切换，执行列表不受 Section 折叠影响。只在面板可见时定时采样，单个 monitor 请求在途时不叠加请求；不启动新的 GUI 观察宿主。

终止通道按 execution ID 定址，调用方只写请求，持有 Popen 的 owner 才发送信号；正常停止与强制终止分别处理。Python 在本机没有 os.waitid，因此采用已通过本机小脚本验证的 macOS libproc 查询。只读 advisor 建议保留未回收 leader，并先确认 zombie、再取得完整组列表，直到只剩 leader 才回收。这能处理主进程先退出而 worker 仍活着的情况，也避免 PID／PGID 复用接管。实现复核发现先取列表再查 zombie 的竞态，现已按这个顺序修正；未引入 waitid 兼容层或后台 daemon。

实施按依赖顺序完成运行时与公开输出、CLI 入口、Swift 模型与呈现，再同步文档及独立版本。检查先静态与小规模脚本，再单次限并发 Swift 构建／既有原生检查，最后复用构建由既有安装工具开发签名安装。不会修改实际项目配置或重置偏好。

验收使用临时目录和低负载 sleep 命令，确认无配置的一次性执行可见、正常结束有真实结果、人为停止有明确原因、强制终止可达、失去 owner 不按 PID 接管、相同名称的无关进程不受影响、CLI JSON 与 Swift 解码一致。主机采样必须有时间与窗口，停止采样不能显示为新鲜；不通过制造真实高负载验证告警。复用适用的既有检查，不增加自动化测试。安装核对 App／CLI 版本、开发签名、实际进程路径与偏好保留，并保留准确的控制范围。

## 实施与当前证据

候选版本为 App 0.4.0／CLI 18.1.0。资源配置 schema 5、旧资源结果版本和具名 run 结果保持原合同；新增 monitor／exec／terminate 均为结果 schema 1，生成 schema、打包 manifest 检查、手册、PRD 与技术合同一起更新。新 [activity 合同](../../docs/product-tdd/activity.md)拥有采样和停止证明，不在 Task Packet 中另建持久解释。

[执行脚本观察](evidence/execution-observation.json)来自修正后的顺序实现：正常退出与日志一致，TERM 得到 human／interrupted／scope-complete；leader 先退出且 worker 忽略 TERM 时保持 descendants-running／running，KILL 后 worker 不再存在；旁边同名 sleep 仍活着；执行者被杀后 owner-lost、不可终止，force 请求没有发送信号。全部使用临时目录与低负载 sleep，未新增测试。

[既有仓库检查](evidence/repository-check.txt)包含静态、类型、七项依赖约束及 260 项现有测试成功。结束判据的最后修正位于新单元，后续单独类型检查与上述脚本重新通过；不声称既有测试覆盖了新停止边界。Swift 首次双任务低优先级构建 7.58 秒成功；最后呈现／调度改动将由现有原生检查同一次增量构建确认。

本轮开始采用自己的 `dev exec` 执行仓库检查及原生检查，保留命名、日志与控制入口。配套 wheel 已建立独立 Library runtime；无自定义 cliPath 偏好，安装后包默认值即可采用新版，无需改写用户偏好。[原生检查](evidence/native-check.txt)的 13 项成功，无条件跳过。它们来自原有测试，其中部分使用透明窗口，不能称整套为无窗口检查；没有新增 GUI 观察宿主。

[App 客户端观察](evidence/app-client-observation.json)使用只含 Foundation 的小脚本编译实际 CLIClient／ActivityStore／模型：真实配套 CLI 成功解码，AppStore 发出的 human 终止请求最后得到 interrupted／scope-complete，结束后不可再终止；CLI 实际退出 130，retry_allowed=false。此脚本不含 AppKit、不创建窗口。[采样开销](evidence/monitor-cost.json)实测单次 monitor 约 0.729 秒墙钟、0.396 秒 CPU；它只在面板可见时约每 5 秒运行，不宣称零开销或严格实时。

96 个 CLI 源／资源文件与已构建 wheel 逐字相同，Swift 二进制摘要与成功原生检查的产物已记录在 [validation](evidence/validation.json)。现有资源 fixture 的浅深色图已检查，包含新页面切换；其中机器概览仍为加载占位，不能用它声称执行页视觉验收已全覆盖。停止链路由上述实际 Store 和 CLI 的证据支持，最终整体体验留给用户安装试用。正式安装与最终交付尚未完成。
